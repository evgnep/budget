# Бюджетирование счетов

Фича реализована. Ниже - модель, правила расчёта и карта реализации.

## Цель

Для счёта с бюджетом показать, **сколько денег можно потратить сегодня**: из текущего
остатка вычесть всё, что уже расписано на будущие дни и отложено под резервы.

Фича включается только для счетов `AccountKind.BUDGET`.

## Входные данные

### На счёте (`AccountBudget`, вложенный объект в `AccountContent`)

- **`replenishDay: Int?`** - число месяца (1..28), когда происходит пополнение / сброс
  лимита. Трактуется как **начало дня** (`00:00`), граница **не включается**: при
  `replenishDay = 1` сброс происходит в начале месяца. `null` - пополнение не задано.
- **`dailyAllowances: List<DailyAllowance>`** - остаток на день (сколько нужно
  откладывать на каждый будущий день).
- **`reserves: List<Reserve>`** - отложенные суммы.

`DailyAllowance` и `Reserve` имеют одинаковую форму:

- `amount: RawMoney` - сумма (целые минорные единицы, в валюте счёта).
- `from: LocalDate?` - начало периода действия, `null` = открыто влево.
- `to: LocalDate?` - конец периода действия, `null` = открыто вправо.

Границы периода **включительные**: `[from, to]`.

Отрицательные суммы разрешены. Условие `from > to` запрещается на форме.

### На элементе операции (`TransactionContent.Item`)

- **`reservedUntil: LocalDate?`** - сумма элемента отложена до этой даты. Сравнение
  **строгое**: резерв действует, пока `today < reservedUntil`. `null` - не зарезервировано.

Смысл: пополнение бюджетного счёта, сделанное заранее (например, за 2 дня до сброса
лимита), не должно влиять на "остаток на день" до момента сброса. Отметку удобно
ставить прямо в окне операции. Авто-подстановка = дата ближайшего сброса
(`replenishDay`) относительно даты операции; поле остаётся редактируемым.

Такой элемент участвует в расчёте остатка счёта как обычно и исключается только из
расчёта "остатка на день".

## Расчёт "остатка на день"

На форме остатков добавляется столбец **"Остаток на день"**. Показывается всегда;
для счетов не-`BUDGET` или без `replenishDay` - пустой.

### Ближайший сброс

`nextReset` - момент `00:00` дня `replenishDay`, строго в будущем:

- `today.dayOfMonth < replenishDay` -> `replenishDay` этого месяца;
- `today.dayOfMonth >= replenishDay` -> `replenishDay` следующего месяца.

Следствие: в день сброса (`today.dayOfMonth == replenishDay`) сброс уже считается
пройденным, `nextReset` уходит на следующий месяц, и диапазон дней разом становится
почти месяц. Это ожидаемо: в день пополнения бюджет считается на весь следующий период.

### Диапазон дней под дневные лимиты

Даты `d`, для которых `today < d < nextResetDate`, то есть
`[today + 1 .. nextResetDate - 1]` включительно.

- Сегодня не входит - сегодняшняя трата и есть то, что показывает столбец.
- День сброса не входит - в `00:00` этого дня деньги уже пришли.

### Лимит на день

Для каждого дня `d` из диапазона берётся один `DailyAllowance`:

- подходящие записи - те, у которых `d` входит в `[from, to]`;
- запись `from == null && to == null` ("без ограничений") имеет **низший** приоритет;
- остальные подходящие записи равноправны, сортируются по паре `(from, to)`, берётся
  первая;
- если ни одна запись не подходит - вклад дня равен `0`.

На форме запрещается заводить больше одной записи "без ограничений".

### Активные резервы

`Reserve` активен, если `today` входит в `[from, to]` (обе границы могут быть `null`).
Суммы активных резервов складываются.

### Зарезервированные элементы операций

По бюджетному счёту суммируются `item.money` (со знаком, без `abs`) всех элементов,
у которых `reservedUntil != null && today < reservedUntil`.

### Формула

```
остаток_на_день = остаток
               - Σ_{d в диапазоне} лимит(d)
               - Σ активных резервов
               - Σ item.money зарезервированных элементов
```

Результат может быть отрицательным - это значит, что обязательств больше, чем денег
на счёте.

### Примеры

Везде остаток `100`, сегодня `1-е`, `replenishDay = 10` -> диапазон дней `2..9` (8 дней).

1. Лимит `6` без ограничений -> `8 * 6 = 48`. Остаток на день = **52**.
2. "до 5-го: `7`", "без ограничений: `6`" -> дни `2..5` по `7` (`28`) + дни `6..9` по
   `6` (`24`) = `52`. Остаток на день = **48**.
3. Условия примера 2 + резерв `1.8.26..31.8.26` на `100` (неактивен, `today` = `1.9.26`)
   + резерв `30.8.26..5.9.26` на `50` (активен) -> `48 - 50` = **-2**.

## План реализации

### `common`

- `event/AccountBudget.kt` - `AccountBudget`, `DailyAllowance`, `Reserve`
  (`@Serializable`). `AccountBudget` вложен в `AccountContentV1` полем
  `budget: AccountBudget = AccountBudget.EMPTY`. Версия контента остаётся `V1` - старые
  события читаются без изменений.
- `TransactionContentV1.Item` получил `reservedUntil: LocalDate? = null` (тоже `V1`).
- Даты сериализуются в ISO (`kotlinx.datetime.LocalDate`).
- `utils/dailyBalance.kt` - `calculateDailyBalance(rest, today, budget, reservedItems)`,
  чистая функция без обращения к БД, возвращает только итог (`RawMoney?`, `null` при
  отсутствии `replenishDay`). `nextResetDate(today, replenishDay)` вынесена отдельно.
  `Instant.toLocalDate(timeZone = currentSystemDefault())` - хелпер там же.
  Список `ReservedAmount(amount, until)` собирает вызывающий код.

### `db-sqlite`

- Flyway `V3__Account_budget.sql`: одна текстовая колонка `budget` на таблице `account`
  с JSON всего `AccountBudget` (`DEFAULT '{}'`); nullable колонка `reserved_until`
  (ISO-текст) на таблице `transaction_item`.
- ktorm-маппинг: `mapping/Accounts.kt` (сериализация `budget` через `Json`),
  `mapping/Transactions.kt` (`reserved_until`).
- `TransactionDao.sumReservedByAccount(accounts, today): Map<AccountId, RawMoney>` -
  `Σ item.money` по счёту, где `reserved_until > today` (строгое сравнение ISO-строк,
  `NULL` не попадает), `transaction_deleted = 0`.

### `desktop`

- `AccountDetailController` + `fxml/account/accountDetail.fxml`: секция бюджета, видимая
  при `kind == BUDGET` - `replenishDay` + две таблицы `{сумма, с даты, по дату}` с
  кнопками добавить/удалить. Даты вводятся ISO-текстом. Валидация: `replenishDay` 1-28,
  `from <= to`, корректность сумм.
- `BalanceController` + `fxml/balance/balances.fxml`: столбец "Остаток на день". Для
  строки счёта берётся остаток на конец периода, `sumReservedByAccount` и
  `calculateDailyBalance`. Пусто для не-`BUDGET` и счетов без `replenishDay`.
- `TransactionDetailController` + `fxml/transaction/transactionDetail.fxml`: столбец
  "Резерв до" в таблице строк (вкладка "Детали"), ISO-текст. Первый простой шаг -
  без авто-подстановки и date-picker, доработаем позже.

### `access-ingester`

Ничего не делает - `AccountContent` строится с бюджетом по умолчанию (пустым).

## Известные компромиссы

- Бюджет хранится внутри `AccountContent` (вариант "всё в счёте"). Значит, правка
  разных резервов в разных "местах" (places) даёт конфликт по всему счёту, а не по
  отдельной записи. Для личного использования это приемлемо; при необходимости
  позже выносится в отдельный `ObjectKind`.
- У `replenishDay` граница не включается (`00:00`), а у `Reserve` период
  включительный (`[from, to]`) - разные конвенции, потому что это разные вещи:
  повторяющаяся граница против явно выбранного диапазона.

## Упрощения (по договорённости «потом исправим»)

* reservedUntil редактируется только на вкладке «Детали»; переключение на структурные вкладки (доход/расход/…) 
  пересобирает строки и сбрасывает резерв. Нет date-picker и авто-подстановки ближайшего replenishDay.
* Столбец «Остаток на день» использует остаток на конец выбранного периода как базу  
  (для периода «за всё время» / заканчивающегося сегодня это сегодняшний остаток).
